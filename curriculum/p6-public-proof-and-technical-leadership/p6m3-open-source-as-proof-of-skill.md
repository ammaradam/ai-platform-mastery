# P6M3 · Open source as proof of skill

**Pillar:** [Public proof and technical leadership](README.md) · **Time:** ~6 h · **Pass mark:** 80% on the quiz

## Learning objectives

- Make MLOps-Toolbox easy to adopt
- Make a first upstream contribution successfully
- Build visibility through useful, small, finished things

## Lesson

## Your own project: MLOps-Toolbox
Adoption depends less on code quality than on: a README that explains the
problem in one paragraph, a 5-minute quickstart, a realistic demo
(PriceCatcher), clear contribution guide, tagged releases, and issues labelled
"good first issue". Write the docs for a stranger.

## Upstream contributions
Start with docs and small fixes in projects you use (vLLM, Feast, Kueue,
OpenTelemetry, Langfuse, Evidently). Steps: read CONTRIBUTING, find a
well-scoped issue, comment before starting, keep the PR small, include tests,
respond to review quickly. One merged PR in a well-known project carries real
signal.

## Small finished things beat big unfinished ones
A published eval dataset, a tiny CLI, a Kubernetes manifest example, a
benchmark notebook — each is shareable proof. Your side-project list is long;
choose open-source work that **reinforces your expertise story** (platform +
evals + Malaysia) and pause the rest.

## Quiz

Answer without notes first. Answers are in the collapsible section below.

**Q1.** What most increases adoption of a small open-source library?

- A) A logo
- B) Rewriting in Rust
- C) More features
- D) A clear README, 5-minute quickstart and realistic demo

**Q2.** Before starting work on an issue in a big project, you should...

- A) Fork and never upstream
- B) Open a 2,000-line PR
- C) Email maintainers privately
- D) Read CONTRIBUTING and comment on the issue first

**Q3.** Which side project best reinforces an "AI platform + evals + Malaysia" expertise story?

- A) A rent tracker
- B) A kids' quiz app
- C) An open Malaysian code-switching eval dataset
- D) A family tree app

**Q4.** What is usually the best first contribution to a large project like vLLM?

- A) Reformatting the codebase
- B) A docs fix or small, well-scoped bug fix with tests
- C) A major new feature
- D) A new logo

<details><summary>Answers and explanations</summary>

- **Q1: D** — People adopt what they can understand and try quickly.
- **Q2: D** — Coordination avoids wasted effort and duplicate work.
- **Q3: C** — It directly showcases the niche you want to be known for.
- **Q4: B** — Small, well-scoped PRs get reviewed and merged, building trust for bigger work.

</details>
